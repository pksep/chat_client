# ADR 001: Реализация кэширования сообщений с использованием IndexedDB

## Статус

Принято

## Контекст

Чат-приложению требовался способ сохранения истории разговора локально, чтобы пользователи не теряли свою историю при обновлении страницы или переходе away и возвращении обратно. Это особенно важно для чат-опыта, где пользователи могут захотеть сохранить контекст между сессиями.

Предыдущая реализация хранила сообщения только в памяти, что означало, что вся история разговора терялась при обновлении страницы или навигации. Это было плохим пользовательским опытом, особенно для длинных разговоров.

## Решение

Мы реализуем локальное хранилище сообщений с использованием IndexedDB по следующему подходу:

1. **Стратегия хранения**: Использовать IndexedDB для хранения сообщений для каждой сессии чата с использованием ID чата как ключа
2. **Структура данных**: Хранить сообщения в структурированном формате, который можно легко извлекать и обновлять
3. **Сериализация**: Обеспечить правильную сериализацию всех данных для избежания ошибок DataCloneError
4. **Стратегия загрузки**: Загружать кэшированные сообщения при инициализации сессии чата
5. **ПERSISTENCE**: Сохранять сообщения в IndexedDB после каждого добавления или обновления сообщения

## Детали реализации

### Схема базы данных
- Имя базы данных: `chat-messages-db`
- Имя хранилища объектов: `messages`
- Путь ключа: `chatId` (UUID)
- Формат хранимых данных:
  ```json
  {
    "chatId": "uuid-строка",
    "messages": [
      {
        "role": "user" | "assistant",
        "content": "содержание сообщения",
        "timestamp": "форматированная метка времени"
      }
    ]
  }
  ```

### Ключевые функции
1. `openDB()`: Открывает или создает базу данных IndexedDB
2. `loadMessages(chatId)`: Получает кэшированные сообщения для конкретного чата
3. `saveMessages(chatId, messages)`: Сохраняет сообщения для конкретного чата
4. `sanitizeMessages(messages)`: Обеспечивает правильную сериализацию сообщений перед сохранением

### Точки интеграции
- **Инициализация**: Загрузка кэшированных сообщений при вызове хука `useMastra`
- **Добавление сообщений**: Сохранение сообщений после добавления новых сообщений в разговор
- **Обновление сообщений**: Сохранение сообщений после обновления ответов ассистента
- **Очистка**: Сохранение пустого массива сообщений при очистке истории разговора

## Рассмотренные альтернативы

### 1. Local Storage
- **Плюсы**: Простой API, широко поддерживается
- **Минусы**: Ограниченный объем хранилища (5-10МБ), поддерживает только строковое хранение, не подходит для сложных объектов
- **Решение**: Отклонено из-за ограничений при работе с комплексными объектами сообщений и объемом хранения

### 2. Session Storage
- **Плюсы**: Автоматически очищается при завершении сессии
- **Минусы**: Действует только в течение сессии страницы, не сохраняется при обновлении
- **Решение**: Отклонено, так как не соответствует требованиям сохранения данных

### 3. Браузерный кэш с пользовательской реализацией
- **Плюсы**: Полный контроль над стратегией кэширования
- **Минусы**: Более сложная реализация, потенциальные утечки памяти
- **Решение**: Отклонено в пользу использования проверенного API IndexedDB

## Последствия

### Положительные
- Пользователи сохраняют историю разговора при обновлении страниц
- Улучшенный пользовательский опыт для длинных разговоров
- Лучшая производительность для часто используемых чатов
- Отсутствие потери данных при переходе away и возвращении

### Отрицательные
- Увеличение сложности сервиса обмена сообщениями
- Потенциальная нагрузка на производительность от операций с базой данных
- Необходимость корректной обработки ошибок IndexedDB
- Дополнительные требования к хранилищу на устройствах пользователей

### Нейтральные
- Никакого влияния на существующие API контракты
- Никаких изменений в интеграции с клиентом Mastra
- Никаких изменений в UI компонентах

## План реализации

1. Создать схему базы данных в функции `openDB()`
2. Реализовать функции загрузки и сохранения сообщений
3. Интегрировать кэширование в хук `useMastra`
4. Добавить обработку ошибок для операций с базой данных
5. Протестировать с различными сценариями сообщений
6. Документировать поведение кэширования для разработчиков

## Будущие соображения

1. **Управление хранилищем**: Реализовать логику очистки старых чатов для предотвращения неограниченного роста хранилища
2. **Стратегия синхронизации**: Рассмотреть синхронизацию с серверным хранилищем для лучшего опыта на нескольких устройствах
3. **Производительность**: Профилировать операции с базой данных, чтобы они не блокировали UI
4. **Резервное копирование/восстановление**: Добавить функциональность экспорта/импорта истории чата
5. **Конфиденциальность**: Рассмотреть возможность реализации опционального кэширования (вкл/выкл)
