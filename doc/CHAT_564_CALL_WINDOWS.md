# CHAT-564 — отдельное окно звонка

Ветка `chat-564`. По уточнению пользователя от 26.11 после проверок нужно слить актуальный main через PR и опубликовать Tauri. Production-веб и сервер отдельно не выкладываются.

## Реализация

- Дочерний DOM монтируется после завершения навигации WebView на собственный `about:blank#sep-chat-call`, а не во временный документ. Временная ошибка доступа к документу другого WebView допускает ожидание; отмена и закрытие прекращают подготовку.
- На Linux включено разрешение автоматических popup WebKitGTK для входящих вызовов. Нативный фильтр разрешает только собственную поверхность; сохраняются related view/configuration/environment и единственный RTC-контроллер.
- Отказ необязательного центрирования (например, на Wayland) не прерывает открытие. Неуспешный показ освобождает скрытую поверхность.
- Закрытие ожидает снятие слушателей; поздний ответ resize не вызывает необработанную ошибку уже уничтоженного окна.
- Каждая поверхность получает уникальное browser window name. Нативный macOS-прогон показал повторное использование WebKit старого именованного контекста после native destroy: второй window.open не вызывал создание нового окна, а следующий IPC получал window not found.
- События `call.window.opening/unavailable/failed/shown/cancelled` записывают этап, длительность, версию/ОС оболочки и ограниченную причину отказа. Переход к встроенной модалке сохраняет звонок.
- В шапке звонка добавлен пин. Включение подтверждается состоянием ОС. На X11 читается EWMH-свойство самого окна: в нативной проверке WM выставлял ABOVE, но и Tao, и GDK возвращали старый false. Внешние процессы для работы кнопки не запускаются. Закрепляется только звонок; fullscreen временно снимает topmost и восстанавливает его при выходе. Новое окно начинает без пина.
- При достаточных размерах области участников Tauri показывает до девяти плиток. Область измеряется после шапки/управления, учтён резерв пагинации. При изменении размера страницы сохраняется видимость первого участника прежней страницы. Политики браузера/Android и качество медиа не менялись.

## Диагностика исходной жалобы macOS

26.11.2026 проверены клиентская телеметрия, chat-server и ограниченная выборка LiveKit WARN в актуальном production-контексте.

Подтверждены Tauri/macOS и успешное подключение; оценка сети после входа — `excellent`. Версия приложения отсутствует в старой телеметрии, причины отказа popup она не записывает. Конкретная причина исходного сеанса пока не доказана. Изменения устраняют найденные риски и добавляют недостающую диагностику; повторный реальный звонок после установки исправления остаётся необходимым. Подробный разбор production-сеанса сохранён в локальном отчёте.

## Комментарии закреплений и поиск

- `PinCommentCard` останавливает dblclick: действие родительского сообщения не запускается; обычные действия карточки сохранены.
- Общий поиск показывает доступные комментарии под оригиналом; поиск внутри чата находит оригинал по тексту заметки и переходит к нему. На сервер отправляется opt-in `includePinComments=true`; это дополнение существующего поиска, не новый API заметок.
- Локально загруженные заметки находятся до сети. Очередь остаётся в общем хранилище CHAT-561; комментарии поиска не записываются поверх подтверждённого состояния. Изменение/удаление или ожидающая команда во время HTTP имеют приоритет над старым ответом. Смена SDK/пользователя отбрасывает ответ. SELF дополнительно фильтруются по владельцу.
- Для поиска заметок во всей истории требуется серверный [PR #253](https://github.com/pksep/chat_server/pull/253). Старый сервер продолжает обычный поиск; локальный поиск по уже загруженным заметкам доступен. Сервер и Android в основной рабочей копии не изменялись; серверное дополнение подготовлено отдельно от чужой ветки chat-563.
- Сервер: 5 интеграционных проверок PostgreSQL, ESLint и сборки общей библиотеки/сервера прошли. Использовалась отдельная база, пользовательские данные не менялись.

Нативная проверка macOS воспроизвела отклонение `about:blank%23sep-chat-call`: WebKit кодирует разделитель фрагмента, и прежний allowlist не принимал запрос. Теперь допускаются только оба точных варианта собственной поверхности и короткое одноразовое подготовленное `about:blank`. Бинарник исходного пользователя и точная причина его старого случая неизвестны.

Часть виртуальных macOS-экранов CI имеет 1024×768: в таком прогоне фактическая область сетки была 1370×511, поэтому корректны шесть плиток. Девять подтверждены на достаточной измеренной площади в Windows native, Mac Intel и браузерных проверках. Размер экрана фиксируется в report.json, а проверка не требует девять на недостаточной площади.

## Ограничения

Tao 0.37.2 не поддерживает topmost на Wayland; кнопка там отключена с пояснением. На X11 решение принимает оконный менеджер. На macOS обычное закрепление не обещает отображение поверх чужих полноэкранных Spaces. Работа самого отдельного окна проверяется независимо от поддержки topmost.

Нативные проверки используют вымышленных участников, отдельные профиль/идентификатор/схему, локальные серверы. Пользовательские сообщения и звонки не изменяются. Проверка синтетического интерфейса не заменяет повторение исходного реального звонка.

Wayland проверен на Weston в CI Ubuntu 24.04, X11 — с Openbox. Hyprland и пользовательское оборудование отдельно не проверялись. Первые Wayland-прогоны падали в UI-процессе WebKit до запроса popup; убраны принудительные renderer-переменные теста, добавлены минимальный GTK/WebKit probe и базовый IPC до загрузки Vue. В этих условиях проверка прошла; влияние каждого изменения окружения отдельно не доказано. Предупреждения GTK о scale factor сохраняются, но в успешном прогоне не прерывают жизненный цикл окна.

Дополнительно Linux Tauri использует существующий CSS-переход темы вместо `startViewTransition`: известен нативный SIGSEGV WebKitGTK 2.52 при отсутствии backing store ([WebKit #321683](https://bugs.webkit.org/show_bug.cgi?id=321683)). JS try/catch от такого падения не защищает. Четыре E2E подтверждают переключение/сохранение темы и выбор CSS только в Linux Tauri; браузер, Windows и macOS сохраняют прежнюю ветку. Это защита известного пути, а не доказательство точной причины исходного пользовательского серого экрана.

## Окно Windows после обновления

NSIS updater 2.14.1 передаёт новой версии исходные аргументы приложения, включая `--autostart`. Прежний startup-код снова скрывал окно в трей. Установщик теперь отмечает обновлённую версию в `Software\<bundle identifier>\Updater`; первый запуск этой версии один раз показывает и разворачивает главное окно. Обычный последующий автозапуск остаётся скрытым. Проверяются HKCU и HKLM, отметка потребления относится к текущему пользователю. QA использует собственный identifier.

Расширенный Windows native smoke прошёл: настоящее обновление NSIS 1.6.100 → 1.6.101 из скрытого/свёрнутого окна открыло окно (`visible=true`, `minimized=false`, `focused=true`), сохранило черновик/сессию и не предложило повторное обновление. Следующий обычный автозапуск вернул `visible=false`. Защищённое восстановление входа/темы и явный выход проверены; рабочие протокол/автозапуск не менялись. Использован свежий QA-пакет 1.6.100 и уже собранный в этом же прогоне подписанный пакет 1.6.101, выбранный по точному имени. Восемь сценариев ярлыков также прошли. Конкретные аргументы исходного пользовательского сеанса не получены; проверен соответствующий путь кода.
