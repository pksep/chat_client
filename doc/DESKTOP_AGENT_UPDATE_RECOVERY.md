# Tauri: выбор папки и блокировка агента при обновлении

## Наблюдения 26.11.2026

На присланном скриншоте обычного ИИ-чата справа был выбор модели, а кнопка
папки слева отсутствовала. `AiComposerSettings` получал `project` только
во вкладке «Агенты»; дополнительно эта вкладка скрывалась при узком окне Tauri.

На скриншоте установщика Давида Перова: `Extract: error writing to file
sep-pi-agent.exe`. Это отказ записи уже скачанного установщика. На собственном
Windows-стенде воспроизведён тот же класс отказа: работающий exe агента нельзя
заменить. Скриншот сам по себе не доказывает состояние процессов или антивируса
на компьютере Давида.

## Исправление

- В настольном Tauri папка доступна слева от модели также в обычном ИИ-чате.
  Узкая ширина окна не отключает локальные возможности. Браузер и мобильные
  платформы кнопку не получают.
- Выбор использует существующий `desktop_agent_pick_directory`. Отмена/отказ
  оставляет текущий чат, модель и черновик. Успех создаёт отдельного локального
  агента; обычная переписка и её черновик сохраняются для возврата.
- Работа агента по-прежнему требует настройки провайдера. Серверный каталог
  обычного ИИ-чата не подменяет подключение локального агента; ключ в установщик
  не добавляется.
- Windows назначает запущенные агенты в собственный неназванный Job Object с
  `KILL_ON_JOB_CLOSE` и `SILENT_BREAKAWAY_OK`. Даже `process::exit` updater и авария
  Tauri освобождают агент. Job не наследуется внешними приложениями, которые агент
  открывает для пользователя, и не содержит установщик.
- Обычный выход очищает сессии агента. Подготовка обновления отклоняется, пока
  идёт открытие папки, настройка или запрос локального агента.
- NSIS после штатного закрытия основного Чата регистрирует в Restart Manager
  только `$INSTDIR\sep-pi-agent.exe`. Это восстанавливает обновление со старых
  версий, уже оставивших процесс. Одноимённые процессы из других каталогов
  не завершаются. При ошибке освобождения установщик прекращает запись файлов.

## Уточнение после публикации 1.59.1

Дополнительный Windows-тест подтвердил, что первоначальный Job также завершал
отдельное приложение-стенд, запущенное агентом **после** назначения в Job. Это
побочный эффект наследования Windows Job, а не зарегистрированная потеря данных
пользователя. В patch добавлен `SILENT_BREAKAWAY_OK`: в Job остаются явно
назначенные процессы агента, а их внешние приложения продолжают работать.
Проверены аварийный выход родителя и явный `stop()`, освобождение exe агента
для установщика и сохранение внешнего приложения. Стенд завершается отдельно.
`cargo test --test desktop_agent_process -- --test-threads=1`: 6 passed
(3 сценария и 3 вспомогательных entrypoint). Новый сценарий сначала воспроизвёл
дефект на опубликованном коде, затем прошёл с исправлением.
Опубликованные файлы 1.59.1 не заменяются; исправление включено в отдельный
patch `1.59.2` (`c5017691`). TypeScript и ESLint повторно прошли перед push.
Пакеты и результаты платформенных проверок:
[Desktop Builds 1.59.2](https://github.com/pksep/chat_client/actions/runs/45838051722),
[релиз 1.59.2](https://github.com/pksep/chat_client/releases/tag/v1.59.2).

Для регрессий используются только собственные QA-пути, синтетическая сессия
и процесс-стенд. Рабочий профиль, `sepchat://` и автозапуск установленного
пользовательского клиента не должны меняться. Нативное управление окном через
Computer Use недоступно; наличие кнопки в личном окне пользователь проверяет
в запущенном полном локальном Tauri. E2E используют синтетический IPC.

В первом полном прогоне с прежним общим QA-identifier окно после обновления
осталось скрытым. Причина отдельно не доказана. Стенд переведён на одноразовый
identifier и профиль, чтобы прежние одноразовые маркеры/хранилище не влияли на
новый сценарий. Изолированный полный прогон прошёл: `visible=true`,
`minimized=false`, `focused=true`; повторного обновления нет. Доказаны
освобождение exe, сохранность черновика/сессии, восстановление входа/темы,
явный выход и скрытый последующий autostart. Протокол и автозапуск рабочего
клиента сверены до/после: не изменились.
