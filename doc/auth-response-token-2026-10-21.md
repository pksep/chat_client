# Вход в Чат при раздельных токенах

## Подтверждённый сбой

После успешного входа локальный клиент возвращался к авторизации. Ответ входа
содержал отдельный токен Чата, но клиент выбирал `erpToken` и передавал его
в запросы к Чату. Сервер отклонял такую сессию с `AUTH_INACTIVE`.

## Правило предотвращения

Для API Чата выбирать непустой строковый `accessToken`, затем `token`.
`erpToken` использовать только как резерв для старого формата ответа.
При единой авторизации эти поля содержат один общий токен, поэтому поведение
остаётся совместимым. Серверные проверки сессии и прав не изменяются.

## Проверки

- `bun test tests/auth-response-token.spec.ts`: пять сценариев для раздельной
  и единой авторизации, резервных полей и некорректных значений.
- `bun x vue-tsc --noEmit`: проверка типов клиента.
- Локальный пользователь `001`: вход, обновление страницы и открытие раздела
  клиентов без повторного перехода к авторизации. Пароль и токены в репозитории
  не сохраняются.
