# CHAT-294: Android, запуск, уведомления и нагрузка

Работа в `chat-294`, созданной от `origin/canary`. Проверяется настоящий debug
APK в Android WebView, системное уведомление и его `PendingIntent`. Продуктивные
серверы и телефоны пользователей не использовались. Системные уведомления
на AVD проверяются для личных чатов (DM).

## Что изменено

- Список из кеша больше не ждёт обновления пользователей и топиков по HTTP.
  Обновление продолжается после первого отображения. Сохранение native-сессии
  и подготовка обоев также не блокируют запуск SDK и Vue.
- Уведомление показывает доступную историю сразу. Скелетон появляется только
  при отсутствии сообщений после проверки кеша. Окно Android ограничено
  72 сообщениями, включая уведомление в уже открытом чате с длинной историей.
- Последняя страница обновляется одним запросом. Контекст запрашивается,
  если нужного сообщения нет в ответе, кеше или уже пришедших событиях.
  Старое уведомление больше не загружает весь промежуток истории до последней
  страницы. Открывается конец чата; старая история остаётся доступной пагинацией.
- Короткий возврат при живом WebSocket сохраняет соединение и не читает повторно
  native-снимки. Разрыв, смена сети и долгое отсутствие сохраняют восстановление.
- Сигналы resume и reconnect используют один цикл обновления. Новый разрыв или
  смена сети во время обновления сохраняют один повтор; ошибка HTTP не поглощает
  уже запрошенную повторную попытку.
- Заголовок подписывается на события записи звонка без GET материалов каждого
  открываемого топика. Материалы запрашивают компоненты звонка при использовании.
- Значки меню статусов загружаются при его открытии. Android сначала использует
  встроенный Noto, вместо скачивания файлов emoji-шрифтов размером 5–11 МБ.
- Удалены двойные обработчики совместимых событий Socket.IO (`newMessage`,
  `messageUpdated` и других): пакет прежде попадал и в `on`, и в `onAny`.
  Входящие `newMessage` и основной серверный `changeMessage` с `type: NEW`
  объединяются с задержкой до 16 мс, максимум
  200 событий в пачке. Перед изменением, удалением или служебным событием пачка
  обрабатывается по порядку; отключение SDK отменяет очередь прежней сессии.
  Повторные native-вызовы очистки уведомлений объединяются с завершающим вызовом.
- Повторное чтение pending notification после установки обработчика закрывает
  промежуток, в котором могло прийти второе нажатие при холодном запуске.

## Стенд и смысл измерений

AVD `chat294_api36`, Android 16 / API 36.1, x86_64 Google Play image,
720×1280, 2 CPU, 2 ГБ RAM, WHPX и программный GPU. Node 22 запускает
Playwright; Bun используется для зависимостей и unit-тестов. Нативный driver
Playwright устанавливается командой `bun x playwright install android`.

Локальный сервер на `127.0.0.1:5188` содержит 4 000 пользователей и
12 × 5 000 сообщений. В IndexedDB заранее сохраняются три истории по 5 000
сообщений. WebSocket настоящий; внешние HTTP-ресурсы WebView блокируются и
учитываются отдельно. Перед каждым итоговым прогоном очищаются данные APK
только на выделенном тестовом эмуляторе.

Подготовка дожидается экрана входа и сохранения синтетической сессии на диск
перед force-stop. Проверка восстановления дожидается запроса истории, затем
ещё четыре секунды наблюдает за возможным повторным циклом. Периодические
AI-запросы сохраняются в журнале и не считаются обновлением справочников чата.

`elapsedMs` включает команды adb и поиск системного уведомления, поэтому
его нельзя выдавать за задержку интерфейса после нажатия. `routeToReadyMs`
измеряет интервал от записи маршрута до кадра с последним сообщением нужного
чата. Холодный `navigationMs` включает загрузку WebView и приложения; это
не время запуска процесса Android. Счётчик кадров скелетона не включает
начальный native splash до подключения отладчика.

Первичная версия Android-этапа подтвердила: ожидание справочников задерживало
список, открытие уведомления вызывало `/around`, обновление справочников и
повторное обновление истории. Поток 300 совместимых событий `newMessage` не
успел отобразиться за 30 секунд — это привело к устранению двойной обработки
и объединению входящих событий в пачки. Итоговая нагрузка использует основной
серверный формат `changeMessage`, включая PTS.

В сценарии холодного списка кеш показан до HTTP справочников, но наблюдалось
32–35 кадров стартового скелетона. Холодный запуск всё ещё требует ускорения:
результаты 8–11 секунд нельзя считать мгновенным открытием. Стенд использует
программный GPU и отладку, на хосте мало свободной памяти. Начальный baseline
снят до исправления подготовки IndexedDB в стенде, поэтому точный процент
ускорения холодного запуска по этим двум прогонам не рассчитывается.

Уведомление без кеша и с отстающей последней страницей сохраняет необходимый
скелетон: один GET последней страницы и один `/around` восстанавливают сообщение.
Периодические запросы фонов, телеметрии и AI не исчезают из Network целиком.
Стенд не моделирует полноценный серверный replay PTS после потери событий.

Финальный контроль `artifacts/chat-294-android-recovery-complete/` завершён
успешно: четыре повторных уведомления и все сценарии ошибок/возврата/нагрузки.
После разрыва соединения выполнены по одному GET пользователей, списка топиков,
закреплений и истории, плюс один health probe. В первоначальном измерении этот
полный цикл выполнялся дважды. Повторных циклов за четыре секунды после этапа
истории не было; скелетонов и кадров чужого чата — 0. Поток 300 сообщений в этом
контроле обработан за 3497 мс без HTTP истории. JSON и итоговый скриншот сохранены.

Повторная серия из 20 уведомлений выше прошла свои проверки, но её проверка
восстановления преждевременно снимала результат через фиксированные 2,5 секунды.
Финальный контроль использует ожидание фактического запроса истории. В подготовке
также устранены гонка сохранения сессии и слишком короткое ожидание начального
экрана. После `device.close()` явно останавливается инструментальный Android
driver: иначе его ADB-сокеты удерживали Node после завершения всех проверок.

## Проверки

Последующая оптимизация холодного запуска и обычных переходов через список
чатов описана в [отдельном отчёте](chat-294-startup-followup.md). В нём используется
обновлённый стенд и собственный APK baseline для сопоставимого измерения.

Сценарии автоматизации: холодный список с задержками справочников по 2,5 с;
холодное и повторное открытие уведомлений при HTTP-задержке 1,2 с;
20 последовательных уведомлений, включая старые; HTTP 503 с доступным кешем;
уведомление, опережающее последнюю страницу; короткий возврат из фона;
три последовательных intent с медленными ответами; поток 300 сообщений;
восстановление разорванного соединения.

Проверяются выбранный чат и последнее сообщение, отсутствие кадров чужого
чата, число запросов, переподключения, скелетоны и предел DOM. Дополнительные
браузерные регрессии проверяют сообщение из кеша при удерживаемом HTTP,
повторное уведомление длинного открытого чата и поздний ответ прежнего топика.

Проверка кода: `vue-tsc --noEmit`, Android Vite build, Capacitor copy и
Gradle assembleDebug выполнены успешно. 18 Bun-тестов проверяют навигацию,
порядок входящих событий, отключение очереди и объединение восстановления;
все прошли. В Android JUnit — 16 тестов, 0 ошибок. После последнего изменения
повторно прошли все 10 браузерных сценариев уведомлений на desktop/mobile.
В расширенном прогоне прошли 70 из 72 связанных браузерных проверок; два
падения точного порога скелетона 300 мс исправлены и отдельно перепроверены
успешно. Это не означает, что весь старый E2E-набор проекта исправлен.

## Локальный корпоративный backend на AVD, 14 сентября 2026

Проверка выполнена на `emulator-5556` (Android 16 / API 36) через корпоративную
ссылку `http://localhost:5188`. ADB перенаправлял `tcp:5188` на локальный
`chat_server` в порту `5001`. В отдельном тестовом аккаунте были созданы четыре
временные группы, 144 сообщения и 16 реакций. После измерений группы удалены.

Пять холодных запусков дали медиану `chat-startup:shell-removed` 1010 мс и p95
1144 мс; медиана `chat-startup:cache-ready` составила 970 мс, p95 — 1079 мс.
Нативный Android `TotalTime` debug APK на программном AVD составил 2388–3379 мс
(p50 2912 мс). Системный запрос разрешения уведомлений был выдан до этой серии
и в результаты не входит.

В 48 переходах между заполненными группами медианный p50 отдельных серий
составил 90,7 мс, худший p95 — 142,4 мс. Зафиксировано 0 кадров скелетона,
0 кадров предыдущего топика, 0 GET истории и 0 GET аватаров во время
переключений, 0 смещения списка после возврата и 0 ошибок страницы. Реакции
присутствовали в первом кадре.

Локальная БД содержит 14 старых MinIO URL аватаров, каждый из которых сейчас
отвечает HTTP 404. Это состояние не подходит для проверки заполнения кеша из
сети. Для изолированной проверки чтения absolute URL из IndexedDB под теми же
ключами были записаны валидные локальные SVG. После холодного запуска все 6 из
6 видимых аватаров присутствовали в первом кадре без сетевого GET. Проверка
также обнаружила, что sticky-аватар мог исчезнуть через 500 мс: общий
`IntersectionObserver` очищал уже декодированный `blob:` URL. `CachedAvatar`
теперь сохраняет готовое изображение при выходе из области наблюдения и
очищает его только при смене `path`. На итоговой APK все 6 из 6 аватаров
оставались готовы и в первом кадре, и через 500 мс во всех 12 переходах.

Итоговый отчёт находится в
`../artifacts/chat-294-android-avd-local-sticky-avatar-fix-2026-09-14/results.json`.
APK: `../artifacts/chat-294-android-avatar-sticky-indexeddb-2026-09-14.apk`,

## Воспроизведение

Требуется отдельный эмулятор: скрипт очищает данные `sep.pksep.app`.
Debug-получатель уведомлений ограничен `android.permission.DUMP` и тестовыми
идентификаторами; в release APK он не входит.

```powershell
bun run build:android
bun x cap copy android
./android/gradlew.bat -p android :app:assembleDebug :app:testDebugUnitTest -PrustorePushProjectId=chat-294-local-performance
adb -s emulator-5556 install -r android/app/build/outputs/apk/debug/app-debug.apk
bun x playwright install android
$env:ANDROID_PERFORMANCE_SERIAL='emulator-5556'
$env:ANDROID_PERFORMANCE_PHASE='local'
$env:ANDROID_PERFORMANCE_STRESS='1'
bun run test:android:performance
bun test test/notificationNavigation.test.ts test/incomingEvents.test.ts test/reconnectRefresh.test.ts
bun run test:notifications:performance
```

JSON, скриншоты и сводка сохраняются в
`../artifacts/chat-294-android-<phase>/`. APK стенда использует тестовый
RuStore project ID. Проверяется обработка системного нажатия; доставка
уведомления через RuStore и поведение физических устройств этим стендом
не измерены. Время debug APK на программном GPU нельзя переносить напрямую
на release APK и конкретный телефон.
