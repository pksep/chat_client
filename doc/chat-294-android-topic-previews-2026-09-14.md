# CHAT-294: холодная главная и компактный кеш топиков Android

Этап выполнен на ветке `chat-294` с Android Studio AVD `emulator-5556`,
Android 16/API 36. Цель — убрать конкурирующую работу IndexedDB сразу после
появления главной страницы и сохранить мгновенный первый кадр топика с
сообщениями, авторами, аватарами и реакциями.

## Найденная причина

После первого содержательного кадра `IntersectionObserver` прогревал все
видимые топики. Для каждого топика он читал полный `topicSnapshots`, а при
наличии старого кеша ещё и полный `topicMessages`. На стенде с 12 топиками по
5000 сообщений один холодный запуск выполнил:

- 12 полных чтений `topicSnapshots`;
- 12 полных чтений legacy `topicMessages`;
- 3 фоновые записи по 5000 сообщений при переносе legacy-кеша.

Работа начиналась после снятия оболочки, поэтому не всегда удлиняла сам
скелетон, но конкурировала за CPU и диск с первым нажатием пользователя. Это
объясняет плавающую задержку первого перехода после холодного запуска.

## Изменение

Версия `chat-sync-shadow-db` поднята с 2 до 3. Добавлено хранилище
`topicPreviews`, в которое атомарно с полным снимком записываются последние
48 сообщений. В превью сохраняются исходные объекты сообщений, включая
`senderUser`, `avatarUrl` и `reactions`.

Фоновый прогрев списка читает только `topicPreviews`. Полный снимок остаётся
источником полной истории при реальном открытии топика. Старый кеш версии 2
совместим: первое открытие читает полный снимок как раньше, а следующая запись
создаёт компактное превью. Удаление истории и сообщения обновляет оба
хранилища; запись выполняется одной IndexedDB-транзакцией.

Измерение того же холодного профиля после изменения:

- 12 маленьких чтений `topicPreviews`;
- 0 чтений `topicSnapshots` из фонового прогрева;
- 0 чтений legacy `topicMessages` из фонового прогрева;
- 0 фоновых записей по 5000 сообщений.

## AVD под нагрузкой

Обычный прогон без CPU-профилировщика показал главную страницу:

- `chat-startup:shell-removed`: 1456,3 мс WebView;
- первый видимый элемент списка: 1517,4 мс WebView;
- сеть до готовности списка: один `GET /config`.

Двадцать переходов между двумя топиками:

- p50 от изменения маршрута до сообщения: 185,1 мс;
- p95: 308,2 мс;
- 0 кадров скелетона;
- 0 кадров предыдущего топика;
- 4 GET истории и 3 GET закреплений за всю серию, по TTL;
- ограничение DOM сохранено на уровне 72 сообщений.

Двадцать системных уведомлений:

- p95 от изменения маршрута до сообщения: 248,8 мс;
- 0 кадров скелетона и предыдущего топика;
- максимум 72 сообщения в DOM;
- ошибок страницы нет.

Дополнительно прошли HTTP 503 с доступным кешем, топик без кеша с нужным
`/around`, короткий возврат из фона, три быстрых notification intent, поток
из 300 WebSocket-сообщений и восстановление разорванного соединения. Поток
из 300 сообщений показал последнее сообщение за 761,2 мс без запроса истории.
Скелетон появился только в намеренно некешированном сценарии и исчез после
получения данных.
