# CHAT-294: чтения кеша и сортировка сообщений

Продолжение работы в `chat-294`, 11 сентября 2026 года. Базовая APK —
итог предыдущего этапа, `chat-294-cold-stage3-after.apk`; копия сохранена как
`artifacts/chat-294-cold-stage4-baseline.apk`. Исходники четырёх изменяемых файлов
до правки находятся в `artifacts/chat-294-stage4-source-before/`.

## Что изменено

- При восстановлении shadow-истории прочтения загружаются один раз. Результат
  используется при наложении состояния на сообщения; обычное обновление
  истории по сети по-прежнему получает свежие прочтения.
- Android выявил параллельный запрос того же состояния из списка топиков.
  Теперь `loadShadowReadState` и `loadShadowSyncMeta` объединяют незавершённые
  чтения одного ключа. После завершения чтение прочтений снова обращается к
  IndexedDB. Ошибка освобождает повторную попытку; новая запись во время
  чтения не затирается его старым результатом. Пользователи разделены ключами.
- Чтение прочтений и диапазонов начинается вместе с загрузкой незавершённых
  вложений и удалений. Эти независимые операции больше не ждут завершения
  всей предыдущей группы. Резидентный подготовленный топик сохраняет быстрый путь.
- Сохранённая в памяти старая отметка прочтения обновляется из IndexedDB при
  гидратации. Изменение прочтения во время чтения снимка тоже учитывается.
- Метаданные незавершённых вложений выбираются по диапазону первичного ключа
  текущего пользователя и топика. Прежний `getAll()` читал все записи,
  включая другие топики и учётные записи, а затем отфильтровывал их в JavaScript.
  Схема IndexedDB не меняется; верхняя граница диапазона открытая.
- Сортировка использует существующий `Date.getTime()` и повторно использует
  разобранные строковые метаданные через `WeakMap`. Замена строки `ex`
  обновляет запись; JSONB-объекты читаются напрямую, поэтому их изменения
  на месте остаются видны. Порядок пересылок, одинаковых timestamps и ID сохранён.
  Кеш удерживает только ID клиента, ID пакета пересылок и порядок в пакете,
  без остальных полей разобранного JSON.

## Проверки

Новые браузерные сценарии выполняются на desktop и mobile:

- 5000 сообщений, 60 одновременных гидратаций, одно чтение снимка и прочтений;
  задержанное чтение вложений не блокирует старт независимых метаданных;
- 5000 чужих записей вложений и две нужные: из IndexedDB передаются только
  две нужные записи, включая идентификатор с `\uffff`;
- устаревшая отметка прочтения в памяти и новое значение другого клиента;
- новое прочтение, пришедшее во время загрузки снимка;
- парная сортировка 5000 сообщений по старому и новому алгоритмам, с
  чередованием порядка запуска и проверкой совпадения всех ID.

Unit-проверки сравнивают 32 400 пар сообщений со старым алгоритмом,
включая JSONB, строки, некорректные метаданные и даты. Проверяются изменения
`ex` и `Date` на месте, а также отсутствие повторного разбора неизменённого JSON.

В первой серии прошли 118 из 120 сценариев. Два новых теста обновления прочтений
использовали второй экземпляр модуля из-за HMR-параметра URL. Исправлено обращение
стенда к реально загруженному модулю: все четыре проверки прочтений прошли.
После уменьшения удерживаемых полей кеша и добавления замера без JSON прошли
20 сценариев кеша и запуска. После дополнительного объединения чтений на
итоговом коде прошли 54 браузерные
проверки кеша и запуска, включая восемь новых случаев общей ошибки, смены
значения во время чтения и разделения пользователей; все прошли.
За этап проверено 138 различных браузерных сценариев в нескольких сериях;
весь старый E2E-набор проекта на итоговом коде не запускался. Финальные
`vue-tsc --noEmit`, все 77 unit-тестов, Vite, Capacitor copy и Gradle
assembleDebug прошли; последний Gradle — 31 секунда.

Парный замер сортировки 5000 перемешанных сообщений, десять раундов с
чередованием старого и нового алгоритма. Каждый раунд использует новые объекты
сообщений; подготовка данных не входит во время сортировки. Ниже медианы:

| Данные                    | Desktop до → после | Mobile до → после |
| ------------------------- | -----------------: | ----------------: |
| Обычные сообщения         |       4,7 → 1,1 мс |      6,1 → 1,5 мс |
| Строковые JSON-метаданные |      34,6 → 5,4 мс |     28,7 → 4,4 мс |

Порядок всех ID совпал. Mobile здесь — браузерная эмуляция Pixel 5, без
замедления CPU. Это измерение одной операции, не всего холодного запуска.

При задержке чтения незавершённых вложений 120 мс независимые метаданные
стартуют до его окончания. 60 гидратаций дают по одному чтению истории,
прочтений и вложений, два чтения sync-метаданных. Из 5002 записей незавершённых
вложений IndexedDB возвращает две нужные, без чтения 5000 посторонних записей.

Первые Android-запуски `shadow-before`, `shadow-after`, `shadow-before-repeat`
сохранены как диагностика: промежуточная APK сократила число чтений прочтений
с трёх до двух, но параллельный вызов списка ещё оставался. Промежуточная APK
сохранена как `chat-294-cold-stage4-provisional.apk`. Её время не относится
к итоговому коду. После объединения вызовов выполнено отдельное сравнение
базовой и итоговой сборок.

## Итоговая проверка Android

Полный прогон `cold-stage4-shadow-after-final` завершился успешно:
49 сценариев, ошибок страницы и внешних HTTP-запросов нет.

| Нагрузка                                  |       p50 |       p95 | Кадры скелетона / чужого чата |
| ----------------------------------------- | --------: | --------: | ----------------------------: |
| 20 переходов между кешированными топиками | 1852,2 мс | 2367,7 мс |                         0 / 0 |
| 20 системных уведомлений                  | 1373,1 мс | 2502,7 мс |                         0 / 0 |

Время измеряется от изменения маршрута до видимого последнего сообщения.
На всех переходах максимум 72 сообщения в DOM. 20 обычных переходов дали
10 запросов истории, не более одного на переход после истечения TTL.
20 уведомлений — 20 запросов последней страницы и два `around` для старых
сообщений, отсутствующих в памяти. Нет запросов промежуточных страниц,
повторной загрузки пользователей/топиков или переподключений при уведомлениях.
Закрепления обновлялись отдельно: 10 и 16 запросов соответственно.
AI, фоны и телеметрия продолжают выполнять свою фоновую работу.

- HTTP 503: кешированный чат открылся без скелетона, один запрос обновления.
- Уведомление без кеша при отставшей последней странице: один `around`,
  нужное сообщение видно через 3576,9 мс, без перебора промежуточных страниц.
  До получения данных скелетон необходим: зафиксирован 51 кадр.
- Короткий уход в фон: 0 запросов пользователей, топиков и истории,
  0 новых соединений; осталась телеметрия.
- Три последовательных intent: открыт последний выбранный топик,
  без скелетонов и кадров чужого чата.
- 300 WebSocket-сообщений: последнее видно через 2171,4 мс от начала
  наблюдения; весь сценарий занял 2485,1 мс. 0 HTTP, 0 скелетонов, DOM ≤72.
- Разрыв WebSocket в фоне: один цикл восстановления пользователей,
  полного списка топиков, закреплений и истории. Дополнительно один
  проверочный запрос списка с `limit=1`; повторного полного цикла нет.
- Тяжёлые отложенные модули и скрытое меню не загружены,
  service worker незавершённых вложений не зарегистрирован.

Скриншоты списка, холодного уведомления и чата после WebSocket-нагрузки
проверены визуально: содержимое и последнее сообщение видны, скелетона
после загрузки нет.

## Холодное открытие и ограничения замера

Контрольная пара после финальной пересборки:

| Метрика                                                  | Базовая APK | Итоговая APK |
| -------------------------------------------------------- | ----------: | -----------: |
| Первый кадр списка от навигации WebView                  |  13828,7 мс |    2825,9 мс |
| Первый кадр холодного уведомления от навигации WebView   |  22970,2 мс |   13158,9 мс |
| Холодное уведомление: маршрут → содержимое               |  16752,9 мс |    8850,4 мс |
| Холодное уведомление: загрузка кеша                      |   8629,3 мс |    2260,0 мс |
| Чтения прочтений активного топика во время загрузки кеша |           4 |            1 |
| Тёплое уведомление: маршрут → содержимое                 |   3428,3 мс |    2808,1 мс |

В ранних диагностических запусках базовая APK читала прочтения три раза;
в последней контрольной паре наблюдаются четыре чтения, включая параллельный
вызов из списка. Итоговая APK читает один раз. Диапазоны, удаления, вложения
и снимок активного топика также читаются по одному разу. Записей кеша до
первого кадра холодного чата нет. Чтение прочтений следующего фонового топика
началось после первого видимого кадра.

Эта пара показывает сокращение лишней работы, но **не доказывает устойчивое
ускорение всего холодного старта**. На хосте зафиксировано всего 485 МиБ
свободной памяти из 16028 МиБ; даже неизменённая базовая APK даёт большой
разброс. Текущий p95 переходов также выше некоторых предыдущих серий, поэтому
заявлять об ускорении всех переходов по этим запускам нельзя. Чтение и
декодирование полной истории, загрузка модулей и задержки WebView остаются
затратами. Нужна повторяемая серия на свободном хосте или физическом устройстве.

Начальная заставка при холодном запуске остаётся. Нулевые скелетоны выше
относятся к переходам с готовыми данными, а не к отсутствующему кешу.

Контроль старого формата кеша на той же итоговой APK также прошёл:
три сценария, без ошибок страницы и кадров чужого чата. Первый кадр списка —
2721,0 мс, холодного уведомления — 8327,4 мс от навигации WebView;
тёплое уведомление — 2234,4 мс от маршрута, без скелетона. Во время холодной
загрузки активный read-state прочитан один раз, записей кеша до первого кадра
нет. Это проверка совместимости, не контрольная пара скорости разных форматов.

## Методика Android

Выделенный AVD `chat294_api36`, API 36, 2 CPU, 2048 МиБ, 720×1280,
программный GPU. Node 22 запускает `scripts/verify-android-performance.ts`.
Стенд содержит 4000 пользователей и 12 топиков по 5000 сообщений;
локально подготовлены истории первых трёх топиков. Задержка справочника
при холодном запуске списка — 2500 мс, истории при открытии уведомления —
1200 мс. Сервер тестовый, реальная серверная нагрузка этим прогоном не измеряется.
Новый флаг `ANDROID_PERFORMANCE_CACHE=shadow` готовит основной кеш;
без него сохранён прежний сценарий legacy-кеша. Оба APK используют одинаковый
стенд и наблюдатель чтений IndexedDB. Подготовка данных не включена в замер.

Время первого видимого содержимого отсчитывается от навигации WebView.
Это не измерение от старта Android-процесса. Уведомления системные, с реальным
PendingIntent; доставка через RuStore и физические телефоны не проверяются.
Хост ограничен по памяти, поэтому весь разброс сохраняется в отчёте.

## Воспроизведение

Из `chat_client`, Bun для unit-тестов, Node 22 для Playwright:

```powershell
bun test ./test
bun x vue-tsc --noEmit
node node_modules/@playwright/test/cli.js test e2e/shadow-read-coalescing.spec.ts e2e/cache-read-scheduling.spec.ts e2e/cache-restoration-performance.spec.ts e2e/cold-start-directory.spec.ts e2e/startup-cache-performance.spec.ts e2e/startup-persistence.spec.ts --workers=1 --reporter=line
```

Android требует выделенный AVD `emulator-5556` с установленной тестовой APK.
Скрипт очищает данные приложения на нём:

```powershell
$env:ANDROID_PERFORMANCE_PHASE='cold-stage4-reproduction'
$env:ANDROID_PERFORMANCE_CACHE='shadow'
$env:ANDROID_PERFORMANCE_BASELINE='0'
$env:ANDROID_PERFORMANCE_PROFILE='0'
$env:ANDROID_PERFORMANCE_TOPICS='1'
$env:ANDROID_PERFORMANCE_STRESS='1'
$env:ANDROID_PERFORMANCE_ASSERT_STARTUP='1'
node --experimental-strip-types scripts/verify-android-performance.ts
```

Для короткого контроля старого формата кеша: `CACHE=legacy`, `TOPICS=0`,
`STRESS=0`, `ASSERT_STARTUP=0`. Для базовой APK дополнительно `BASELINE=1`.
При замерах одновременно не выполняются сборка и браузерные тесты.
Сводка пересоздаётся из корня workspace командой
`python artifacts/summarize-chat-294-cold-stage4.py`.
