# CHAT-294: холодный запуск главной страницы Android

Продолжение в `chat-294`. Приоритет — убрать ожидание поверх уже готового
списка чатов и сократить задержку запуска WebView. Базовая APK — итог этапа 4,
сохранённый как `artifacts/chat-294-cold-stage5-baseline.apk`.

## Причины и изменения

На первом открытии без кеша `fetchAllTopics` получал список, затем ожидал
создания «Избранного», его закрепления, повторного запроса списка и
восстановления звонков. Корневая стартовая оболочка снималась только после
всей этой цепочки. Задержанное создание «Избранного» воспроизвело зависший
скелетон и для непустого, и для пустого списка.

Первичная загрузка списка теперь передаёт границу первого кадра в
`fetchAllTopics`. Полученный список становится готов сразу; дополнительная
подготовка начинается после показа. Для обычных вызовов сохранено ожидание
всей операции. Перед отложенным запуском проверяются текущие SDK и
пользователь. При ошибке дополнительной работы готовый список остаётся виден.
Авторизация, загрузка самого списка и проверка маршрута не пропускаются.

В production-сборке обнаружилась ещё одна последовательная зависимость:
Vite помещал общий помощник динамического импорта в большой `vendor`.
Из-за этого маленький ранний старт Android выполнял библиотеки `vendor`
и Vue перед обращением к native-мосту. Помощник вынесен в отдельный модуль
размером 1142 байта. Стартовый entry теперь имеет только эту статическую
зависимость. Полный статический граф раннего entry сократился с 755870 до
8333 байт; это объём кода до native-проверки, а не размер всего приложения.

Новый Vite-плагин добавляет в HTML предзагрузку обязательного графа `main`
и его стилей. Файлы загружаются параллельно с выбором native-маршрута;
`modulepreload` не выполняет код приложения. Динамические зависимости
звонков, PDF и дополнительных окон в предзагрузку не входят. Общий объём
обязательного приложения этим изменением не уменьшается.

## Проверки

На исходном коде оба мобильных сценария с задержанным созданием
«Избранного» воспроизводили оставшийся `#startup-shell`. После исправления
все четыре проверки desktop/mobile проходят: оболочка снимается при
заблокированном запросе, строки списка доступны, чат можно открыть до
завершения создания «Избранного». Для пустого списка нет оставшихся
скелетонных строк. Создание выполняется один раз, повторный запрос списка
после него сохранён.

Production-проверка задерживает выполнение стартового entry и подтверждает,
что обязательные файлы уже загружаются, а `main` ещё не выполняется.
После снятия задержки появляется реальный экран входа. На desktop и mobile
нет повторных запросов JS/CSS, ошибок страницы и загрузки отложенных
модулей звонков/PDF/окон создания.

Все 77 unit-тестов, `vue-tsc --noEmit`, 28 связанных браузерных регрессий
и две проверки production-сборки прошли. Vite, Capacitor copy и Gradle
assembleDebug также прошли; Gradle — 47 секунд.
В четырёх контрольных Android-прогонах прошли по четыре сценария и отдельная
проверка экрана входа после очистки данных: всего 20 проверок запуска.
Ошибок страницы, внешних HTTP и кадров чужого топика нет. Тёплые уведомления
прошли без скелетона. Полный нагрузочный прогон из 49 сценариев этапа 4 в этом
этапе не повторялся; здесь проверяется именно холодное открытие.

## Результат на главной странице

Повторная пара с заранее выданным разрешением уведомлений:

| Сценарий                                                               |         До |     После |
| ---------------------------------------------------------------------- | ---------: | --------: |
| Экран входа после очистки данных: снятие оболочки                      |  1422,8 мс | 1327,3 мс |
| Главная с кешем: первый видимый список                                 |  1248,6 мс | 1241,1 мс |
| Главная без кеша, медленное создание Избранного: первый видимый список | 10678,6 мс | 3851,4 мс |
| Холодное уведомление: первый видимый чат                               |  3501,9 мс | 4192,1 мс |
| Тёплое уведомление: маршрут → содержимое                               |  1285,0 мс | 1294,4 мс |

Кроме последней строки, время отсчитывается от навигации WebView.
В проблемном сценарии первого списка выигрыш — 6827,2 мс (около 64%).
Сама оболочка в новой APK снялась через 2911,5 мс, следующий зафиксированный
видимый кадр списка — через 3851,4 мс. Счётчик кадров со скелетоном: 342 → 15;
он зависит от частоты кадров и не является самостоятельной мерой времени.

На базовой APK создание Избранного закончилось примерно за 1730 мс до
снятия оболочки: после создания оставалось дождаться закрепления и
обновления списка. На новой оболочка снята примерно за 6363 мс до завершения
создания. CDP-калибровка в этой паре заняла 60 и 629 мс соответственно;
даже с неопределённостью её половины порядок событий не меняется.

В первой паре готовность WebView в том же сценарии была 12304,3 → 5544,8 мс,
но её нельзя выдавать за доступный пользователю экран из-за системного диалога.
Список с кешем в первой паре: 1518,6 → 1963,9 мс; экран входа:
1762,9 → 1604,0 мс. Общего устойчивого ускорения всех вариантов запуска
эти серии **не подтверждают**; холодное уведомление в повторной паре было
медленнее. Подтверждённый основной результат — устранение ожидания фонового
создания Избранного поверх готовой главной страницы.

Скриншоты повторной пары проверены: экран входа и список чатов отображаются,
системного диалога поверх итогового списка нет. После добавления проверки
появления Избранного по завершении операции повторно прошли четыре
браузерных сценария. Список остаётся доступным до завершения, а созданное
Избранное затем появляется без повторного создания.

## Методика

Выделенный AVD `chat294_api36`, образ Android 36.1, 2 CPU, 1536 МиБ, 720×1280,
программный GPU. На хосте 16028 МиБ RAM; при запуске эмулятора свободно
2586 МиБ, во время контроля зафиксировано 568 МиБ. Сборки и браузерные тесты
не запускались одновременно с Android-замерами. Времена предыдущих этапов
на другом состоянии хоста не служат прямой базой сравнения.
Стенд содержит 4000 пользователей и 12 историй по 5000 сообщений;
для сценариев с кешем сохранены первые три истории.

Проверяются отдельно:

- самый первый запуск после очистки данных — до готового экрана входа;
- холодное открытие главной страницы с кешем и задержкой справочника;
- холодное и тёплое открытие чата из системного уведомления;
- холодный список без кеша: список задержан на 1200 мс, создание
  «Избранного» — на 5000 мс, справочник — на 2500 мс.

Первый запуск сохраняется отдельно в `first-install.json`. Время от команды
старта процесса до обнаружения готового экрана включает задержку подключения
автотеста; более узкая отметка снятия оболочки берётся из самого WebView.
В сценарии первого списка возраст отметки снятия оболочки в монотонных часах
WebView связывается с серединой CDP-запроса на хосте. Сохраняется длительность
этого запроса: часы Android и Windows напрямую не сравниваются. Сценарий
начинается после очистки данных приложения, затем сохраняется только сессия
и конфигурация, без пользовательского кеша.
Задержки заданы на локальном тестовом
сервере; реальная серверная нагрузка этим сравнением не измеряется.

Файлы исходного состояния находятся в `artifacts/chat-294-stage5-source-before/`.

Первый диагностический `cold-stage5-before` не используется для сравнения
списка без кеша: выборочная очистка позволяла восстановить список и не
воспроизводила необходимое начальное состояние. В нём также обнаружено
расхождение настенных часов хоста и Android. Исправлены подготовка стенда
и сопоставление времени; production-код для этого не менялся.

В первой исправленной паре (`before-control` / `after`) поверх WebView
открылся системный запрос разрешения уведомлений. Отметки готовности WebView
сохранены, но для проверки действительно доступного экрана используются
повторные запуски `before-repeat` / `after-repeat` с заранее выданным разрешением.

## Воспроизведение

Из `chat_client`:

```powershell
bun test ./test
bun x vue-tsc --noEmit
node node_modules/@playwright/test/cli.js test e2e/cold-list-readiness.spec.ts e2e/cold-start-directory.spec.ts e2e/native-startup.spec.ts e2e/startup-ui.spec.ts e2e/notification-performance.spec.ts --workers=1 --reporter=line
bun run build:android
node --experimental-strip-types scripts/verify-startup-bundle.ts
```

Android: выделенный тестовый эмулятор с установленной APK. Данные приложения
будут очищены. Не запускать сборку и браузерные проверки одновременно с замером.

```powershell
$env:ANDROID_PERFORMANCE_PHASE='cold-stage5-reproduction'
$env:ANDROID_PERFORMANCE_CACHE='shadow'
$env:ANDROID_PERFORMANCE_FIRST_LIST='1'
$env:ANDROID_PERFORMANCE_BASELINE='0'
$env:ANDROID_PERFORMANCE_PROFILE='0'
$env:ANDROID_PERFORMANCE_TOPICS='0'
$env:ANDROID_PERFORMANCE_STRESS='0'
$env:ANDROID_PERFORMANCE_ASSERT_STARTUP='0'
node --experimental-strip-types scripts/verify-android-performance.ts
```

Для базовой APK `BASELINE=1`: замер сохраняет прежнее ожидание «Избранного».
Новая APK обязана снять оболочку до завершения этой операции.
