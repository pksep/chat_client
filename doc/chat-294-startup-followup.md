# CHAT-294: продолжение ускорения запуска и переходов

Работа продолжена в существующей `chat-294` от `origin/canary`.
Базовый APK до этого этапа сохранён в `artifacts/chat-294-startup-baseline.apk`.

## Подтверждённая лишняя работа

Профиль настоящего Android WebView показал повторные измерения ширины окна при
создании компонентов, вычисление ширины строк списка чатов и форматирование дат.
Сетевой журнал загрузки ресурсов подтвердил загрузку `NewContactModal`,
`NewBotModal`, `NewGroupModal` при закрытых окнах. На мобильном экране одновременно
монтировался скрытый CSS desktop-список. Пустой ответ списка активных звонков
загружал LiveKit и MediaPipe. Профиль холодного уведомления также показал заметную
стоимость чтения, преобразования и сохранения длинной истории в IndexedDB.

## Изменения

- Desktop-меню монтируется только при соответствующей ширине экрана.
  Мобильный список остаётся на месте; изменение ширины переключает интерфейс.
- Окна создания чата, бота и группы загружаются при первом открытии. После этого
  экземпляры сохраняются, включая прежнюю анимацию закрытия и состояние формы.
- `useResizeState` разделяет измерение ширины и один обработчик resize между
  компонентами. После удаления последнего потребителя обработчик снимается.
- Формат времени больше не создаёт Intl-форматтер для каждой строки. Даты
  используют общие форматтеры с локальным смещением конкретной даты, сохраняя
  переходы DST и смену часового пояса.
- Список чатов измеряет переполнение всех описаний перед изменением их CSS-классов.
  Это устраняет чередование записей стилей и принудительной разметки строк.
- Одновременные восстановления истории объединяются по пользователю и топику.
  Объём видимого окна каждого потребителя учитывается, полная история сохраняется.
- Мобильное открытие получает 72 сообщения одним HTTP вместо последовательных
  страниц на 48 и 72. Первый кадр по-прежнему использует 48 сообщений.
  Возврат в длинную резидентную историю на desktop также обновляет окно одним
  запросом. Расширение DOM использует уже полученные данные; актуальность,
  непрочитанные сообщения и загрузка истории при прокрутке сохраняются.
- Пустая синхронизация звонков не загружает LiveKit, когда нет локального,
  серверного или сохранённого звонка. Существующие звонки продолжают синхронизацию.
- Ранний Android-загрузчик передаёт приложению и пустой результат проверки
  уведомления. Обычный запуск больше не ждёт повторный native-вызов перед Vue;
  ошибка bridge сохраняет повторную попытку, проверка новых intent после
  подключения слушателя остаётся на месте.
- Метки `chat-startup:*` доступны в Performance для этапов bridge, модулей,
  монтирования Vue, чтения кеша и готовности контента. Android-стенд сохраняет
  ресурсы, опциональный CPU-профиль и обычные переходы через список чатов.

## Android: сравнение APK

Один выделенный AVD Android 16/API 36.1: 2 CPU, 2 ГБ RAM, 720×1280,
программный GPU. Локальный стенд: 4000 пользователей, 12 топиков, по 5000
текстовых сообщений. Задержка справочников при холодном списке — 2500 мс,
истории при открытии уведомления — 1200 мс. Сборки и браузерные тесты во время
этих замеров не запускались.

В свежий топик возврат выполняется без HTTP истории. После истечения 15 секунд
обновление остаётся необходимым, но выполняется одним GET вместо пары 48→72.
Закрепления также обновляются по сроку свежести. Нужная телеметрия, AI и фоны
не исключены из журналов. Ни одного обновления справочников или переподключения
при обычных переходах и сериях уведомлений не было.

В обоих обновлённых APK прошли все сценарии: 20 обычных переходов, 20 системных
уведомлений, HTTP 503 с кешем, уведомление без кеша с отставшей последней страницей,
короткий возврат из фона, три быстрых intent, 300 событий `changeMessage: NEW`
и восстановление разрыва соединения. Восстановление выполняет по одному GET
пользователей, топиков, закреплений и истории. Скелетоны на кешированных переходах,
кадры чужого чата и ошибки JavaScript отсутствуют; DOM ограничен 72 сообщениями.
Без кеша и с отставшим сервером необходимый скелетон сохраняется до получения данных.

Удалённые ранние загрузки окон и SDK сократили сумму размеров запрошенных
JS-файлов примерно с 4,72 до 3,93 МБ. Это несжатые файлы внутри APK, а не трафик
серверного API. LiveKit/MediaPipe загружаются при наличии звонка; создание чата,
бота и группы продолжает работать при открытии соответствующего окна.

Общее ускорение холодного запуска нельзя оценивать одним процентом: первый
дополнительный baseline дал 7836 мс для списка и 7547 мс для кадра уведомления,
а полный baseline — 10 415 и 9743 мс. Измерения заметно зависят от чтения кеша,
локальных ресурсов и состояния хоста. Удаление повторного native-ожидания
подтверждено метками; мгновенным весь холодный запуск на этом AVD пока не стал.
Число кадров холодного скелетона также нельзя сравнивать как его длительность:
частота кадров между прогонами различается.

Дополнительный контроль того же итогового APK после завершения нагрузки,
без новой сборки: холодный список 6934 мс, первый кадр холодного уведомления
8556 мс. Подготовка уведомления перед Vue заняла 10,5 мс. Таким образом,
два замера итоговой сборки дали 6,9–9,3 с для списка и 7,4–8,6 с для кадра
уведомления. В этой серии ошибок JavaScript не было; тёплое уведомление
открылось без скелетона. Чтение и преобразование длинной истории, обработка
основного JS и загрузка локальных ресурсов остаются заметной частью запуска.

фиксируется при подтверждении видимого списка стендом и может включать задержку
опроса Playwright. Полное время запуска процесса Android этим числом не является.

## Проверки и воспроизведение

### Проверки кода и браузера

- 23 Bun-теста форматирования времени, resize, уведомлений, входящих событий
  и восстановления соединения прошли. Отдельно прошёл тест отложенного SDK звонков.
- 48 браузерных проверок на итоговом коде прошли: по 60 переходов с историей
  на 5000 сообщений, 1000 потребителей HTTP, 60 параллельных восстановлений
  IndexedDB, 10 000 непрочитанных, ошибки, офлайн и гонки уведомлений.
- Две проверки полного интерфейса прошли: ленивое открытие/повторное открытие
  окон создания на desktop и переключение мобильной/desktop-разметки при resize.
- Шесть браузерных проверок раннего Android-загрузчика прошли: пустой ответ,
  уведомление и недоступный bridge на desktop/mobile.
- Финальные `vue-tsc --noEmit`, Android Vite build, Capacitor copy и
  Gradle `assembleDebug` прошли. Нативный Java-код этим продолжением не изменялся.
- В серии из 60 переходов p95 составил 280,1 мс на desktop и 258,8 мс в мобильном
  браузере. Лишних HTTP и кадров скелетона — 0; DOM и количество обработчиков
  после GC не выросли. Это отдельный прогон, а не прямое сравнение с прежней
  серией из 300 переходов.

Результаты браузерной нагрузки сохранены в
`artifacts/chat-294-startup-browser-results/`. Старый E2E-набор проекта целиком
не объявляется зелёным: известные ограничения перечислены в общем аудите.

### Команды Android

Сборка и отдельный AVD описаны в [предыдущем отчёте](chat-294-android-performance.md).
Для измерения обычных переходов на установленном APK:

```powershell
$env:ANDROID_PERFORMANCE_PHASE='startup-local'
$env:ANDROID_PERFORMANCE_BASELINE='0'
$env:ANDROID_PERFORMANCE_PROFILE='0'
$env:ANDROID_PERFORMANCE_TOPICS='1'
$env:ANDROID_PERFORMANCE_ASSERT_STARTUP='1'
node --experimental-strip-types scripts/verify-android-performance.ts
```

`ANDROID_PERFORMANCE_PROFILE=1` включает CPU-профиль холодных сценариев; такие
измерения нельзя напрямую сравнивать с прогонами без профилирования.
`ANDROID_PERFORMANCE_STRESS=1` дополнительно включает сценарии уведомлений,
HTTP 503, быстрых intent, 300 сообщений и восстановления соединения.
`ANDROID_PERFORMANCE_BASELINE=1` разрешает записать прежние повторные запросы
обычного перехода. Для новой сборки этот флаг выключен: проверка требует не
более одного запроса истории на переход после истечения срока свежести.

В этой версии стенда локальные ресурсы APK больше не проходят через Node:
перехватываются только внешние адреса. Поэтому сравнивать время с прежними
отчётами как эффект продуктовой оптимизации нельзя. Baseline и новый APK
нужно запускать одним скриптом, без CPU-профиля и параллельных сборок.

Стенд очищает данные только выделенного эмулятора. Внешние ресурсы WebView
блокируются и записываются отдельно; физические устройства и доставка RuStore
не проверяются. Скрипт измеряет готовность контента внутри WebView, а не полное
время запуска процесса Android. Время adb и открытия шторки записано отдельно.
