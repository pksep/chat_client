# CHAT-294: очистка обработчиков редактора

`@pksep/yui@0.1.318` подключается приложением через ES-модуль. Его
FormattingToolbar подписывается на `ownerDocument.selectionchange`, но при
unmount получает DOM через уже уничтоженный родительским ContentEditor
`editor.view`. Снятие обработчика пропускается. Документ удерживает замыкание
панели, редактор и скрытый emoji-picker со всеми DOM-узлами и событиями.

Воспроизведение на реальном MessageList: 300 переходов между тремя топиками
по 5000 сообщений. После принудительной сборки мусора desktop JS heap вырос
с 35,9 до 621,7 МБ, DOM — с 18 214 до 1 538 314 узлов, обработчики — с 10 206
до 966 006. Снимок heap на 10 переходах подтвердил цепочку
`Document → selectionchange → FormattingToolbar → editor → emoji-picker`.

Патч сохраняет DOM, на котором были установлены события, и использует его
для удаления всех подписок при замене редактора и unmount. Ссылка затем
очищается. Жизненный цикл редактора, черновиков и вложений сохраняется.

Изменение хранится в `patches/@pksep%2Fyui@0.1.318.patch`, закреплено в
`package.json` и `bun.lock` через `patchedDependencies` и применяется обычным
`bun install`. Исправляется ES-модуль, используемый Vite; UMD-сборка пакета
не изменяется. При обновлении UI-kit нужно перенести исправление в исходник
FormattingToolbar или повторно проверить патч. Публикация стороннего пакета
для установки проекта не требуется.

Регрессионная проверка:

```powershell
$env:PERFORMANCE_SWITCHES='300'
bun run test:performance --grep 'длинная история'
```

Тест проверяет число запросов, скелетоны, скорость, видимый DOM и рост heap
после GC. Для диагностики доступны `PERFORMANCE_CPU_PROFILE=1` и
`PERFORMANCE_HEAP_SNAPSHOT=1`. Снимок памяти создаётся только для синтетических
данных тестового стенда. Порог heap <20 МиБ учитывает прогрев; дополнительно
число DOM-узлов после GC не должно увеличиваться более чем на 1000.
Общий таймаут теста учитывает `PERFORMANCE_SWITCHES`: минимум 90 секунд,
далее 30 секунд подготовки + 1 секунда на переход. Порог p95 <800 мс
проверяется независимо от длительности всего прогона.

## Панель эмодзи при открытии топика

Профиль Redmi Note 13 Pro показал, что ContentEditor создавал скрытую панель
эмодзи при каждом монтировании. Даже топик с одним системным сообщением
создавал около 4100 DOM-элементов. В полном мобильном цикле возврат к списку
уничтожает редактор, поэтому эта работа повторялась при каждом входе.

Дополнение к тому же патчу создаёт внутренний picker после первого нажатия
на смайлик. Повторное открытие сохраняет экземпляр панели в рамках редактора;
при уходе из топика редактор и панель уничтожаются прежним способом.
Позиционирование выполняется существующим обработчиком после `nextTick`.
Проверены вставка эмодзи, повторное открытие, изоляция и восстановление черновиков.
Регрессия: `e2e/topic-composer-performance.spec.ts`.

## Отложенная загрузка PDF worker

Тот же ES-модуль содержит worker PDF.js в строке base64 размером 2 881 568
байт. `scripts/externalize-ui-kit-pdf-worker.ts` во время Vite build находит
этот литерал по содержимому `WorkerMessageHandler`, декодирует без изменения
кода и лицензии и выпускает отдельный `assets/pdf-worker-<hash>.js`.
URL подставляет Rollup. Расширение `.js` совместимо с MIME и immutable-кешем
существующей конфигурации nginx; worker остаётся модулем JavaScript.

В dev-режиме пакет не преобразуется. В production worker исключён из PWA
precache: загрузка происходит при открытии PDF, затем применяется CacheFirst
с максимумом двух версий и сроком 30 дней. Основной PDF.js пока остаётся
в UI-kit. При обновлении зависимости требуется повторить проверку:

```powershell
bun run test:pdf-worker
bun run build
```

Первой команде нужен Node 22 с поддержкой `--experimental-strip-types` и
установленный Chromium Playwright. Она собирает отдельный production-стенд,
проверяет отсутствие worker в начальных запросах, реальный Worker, геометрию
и синие пиксели двух страниц, повторное открытие без дополнительных запросов.
Браузер и preview на порту 5179 закрываются после проверки. Проверка не
обращается к серверу приложения; артефакты находятся в `../artifacts`.
