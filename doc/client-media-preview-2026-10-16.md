# Входящие изображения в разделе «Клиенты»

## Инцидент

Изображение клиента из MAX или Telegram могло отображаться в сообщении,
затем пропадать. При открытии в просмотрщике вместо фотографии появлялась
заглушка. Отправленная оператором картинка выглядела нормально благодаря
локальному предпросмотру.

## Причина

- Приватные вложения имеют путь `manager-private/<UUID>` без расширения.
  Просмотрщик не получал явный тип медиа и не распознавал изображение.
- Для миниатюры выполнялся авторизованный запрос, но оригинал открывался
  напрямую без заголовка авторизации.
- Прогрев истории и повторный монтаж сообщения независимо загружали один
  файл. Каждая загрузка создавала новый `blob:` URL и через минуту отзывала
  предыдущий, который ещё использовался сообщением или просмотрщиком.

## Исправление и правило предотвращения

Приватное изображение открывается только после авторизованной загрузки.
Просмотрщик получает тип изображения из метаданных сообщения, а не из
расширения приватного адреса. Одновременные запросы одного файла объединяются,
повторная успешная проверка доступа сохраняет действующий временный адрес.

При каждом открытии проверяется право на файл. Ответы 401, 403 и 404 удаляют
временный адрес; временный сбой сети не уничтожает уже показанную фотографию.
Выход, смена учётных данных или сервера очищают временные адреса. Поздний ответ
предыдущей сессии не восстанавливает изображение. Обновление токена запускает
повторную загрузку видимых фотографий без перезахода в переписку.

Содержимое приватных вложений остаётся только в памяти вкладки, без записи
в IndexedDB. Доступ на сервере не ослаблен. Серверные изменения и миграции
для этого исправления не требуются.

## Автоматическая проверка

`e2e/manager-media.spec.ts` воспроизводит приватный файл и отказ при запросе
без авторизации. Проверяются просмотр и скачивание, повторная загрузка
истории, параллельный прогрев, работа через 61 секунду, отзыв доступа,
временная недоступность, смена пользователя, обновление токена и поздний
ответ после выхода. До исправления проверки просмотрщика и прогрева падали.

```sh
bun run test:e2e --config playwright.manager.config.ts
bun run lint
bun run build
bun test ./test
```

Набор Playwright также проверяет обычные изображения, HEIC, PDF, видео,
скачивание и общие компоненты сообщений. Используется отдельный локальный
сервер с одним тестовым потоком; production и реальные сообщения ботов
не затрагиваются.

Итог на рабочей ветке `client-media-preview`: 20 браузерных тестов успешны,
0 упавших, 0 пропущенных. `bun run lint` и `bun run build` завершены успешно.
Сборка сохраняет существующие предупреждения о размере чанков. В изолированной
странице редактора остаётся предупреждение Vite о spellcheck worker;
проверки отправки и вложений проходят.

Полный `bun test ./test`: 175 успешных, 31 упавший, 0 пропущенных.
Те же 31 падение воспроизведены на чистом `canary`:
`13f5560bdf7bd6acff5a730d44a93f79583f3cab`. Они относятся к существующим
тестам multipart-загрузки, переходов из уведомлений и потока AI.
Полный набор unit-тестов не считается успешным; эти изменения его не чинят.
