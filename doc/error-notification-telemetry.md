# Диагностика плашек ошибок

`notification.error.shown` записывается при показе плашки типа `error`
через `showNotification` или `showErrorNotification`. Текст и поведение плашек
не меняются. Событие сохраняется в существующей очереди телеметрии до отправки,
в том числе при перезагрузке страницы.

Поля payload:

- `title`, `description` — строковый текст уведомления;
- `errorName`, `errorMessage`, `errorCode`, `errorStack` — доступные сведения
  об исходной ошибке; объекты запросов и ответов целиком не сериализуются;
- `notificationStack` — место вызова плашки, включая имя файла сборки и позицию;
- `source` — явно переданный источник, когда он известен.

Пользователь, время, устройство, страница, вкладки, состояние звонка во вкладках
и сеть добавляются существующим механизмом телеметрии.

Ошибки `managerRequest` дополнительно создают `network.request.failed`:
`requestPath`, `method`, `elapsedMs`, `timeoutMs`, `httpStatus`, `phase`.
`phase` различает запрос, чтение тела ответа и ошибку HTTP.
Исходная ошибка и её плашка связываются общим `trace_id`, если вызывающий код
сохранил объект ошибки. Фоновое обновление обращений передаёт его явно,
с источником `manager.inquiries.refresh`.

Для остальных источников запросов HTTP-метаданные автоматически не добавляются:
сначала использовать `notificationStack` и `errorStack` для поиска места вызова.
URL записываются без query, fragment и учётных данных. Заголовки и тела запросов
не передаются; известные токены в строках маскируются.

Поиск в production Loki:

```logql
{namespace="erp", service_name="chat-server"}
  |= "client_telemetry"
  |= "notification.error.shown"
```

Ограничить запрос нужным временем и UUID пользователя. После нахождения события
запросить тот же интервал с фильтром по его `trace_id`, чтобы сопоставить плашку
с `network.request.failed`. Отсутствие события не доказывает отсутствие ошибки:
клиент мог ещё не отправить очередь или работать на предыдущей версии приложения.
