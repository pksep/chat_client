# Диагностика истории, доставки и прочтения

События поступают через существующую клиентскую телеметрию в production Loki. Они появятся после выкладки веб-клиента или установки APK/Tauri с этими изменениями. Обновление сервера не требуется. Тексты сообщений, вложения и ответы с текстом ошибок не записываются.

Во всех событиях общий `context.runtime` различает `browser`, `tauri` и `capacitor`. `context.os` (также в `context.device`) содержит `windows`, `linux`, `macos`, `android`, `ios` или `unknown`. Tauri получает ОС через нативную команду: `osSource: tauri_native`. До ответа команды и в старых сборках без неё используется `navigator` / `user_agent_data`; у Capacitor — `capacitor`. Поэтому исходные `platform: web` и `isNative: false` сами по себе не отличают Tauri от браузера: для этого нужен `runtime`. Строка User-Agent не используется для определения Tauri.

Искать по `user_id`, `session_id`, `device_id` и `payload.topicId`. `diagnosticVersion: 1` обозначает эту версию диагностики. `traceId` / `payload.viewId` связывает события одного посещения чата; запрос истории и каждая попытка доставки имеют свои `traceId`. Сопоставлять их нужно также по ID сообщений и чата. Клиентское `occurred_at` и серверное время приёма могут различаться.

| Событие | Что проверять |
| --- | --- |
| `chat.history.resolved` | `source`: сеть, память, IndexedDB, офлайн-кэш, возврат сохранённой истории после ошибки. `response` — нормализованный ответ SDK до объединения с изменениями из WebSocket, `result` — результат загрузки, `window` — текущее окно в хранилище клиента. Флаги запроса, курсоры, длительность и `skipSave` объясняют способ загрузки. Источник `network` может использовать подготовленный нативный ответ; это не доказательство отдельного HTTP-запроса. |
| `chat.message_view.opened` | Начало посещения и новый `viewId`. |
| `chat.message_view.snapshot` | `loaded` — окно отображения, `resident` — сообщения в памяти, `visible` — ID из видимой области, `lastVisible` — последняя непустая видимая область. `includesLatestKnownMessage` показывает наличие последнего известного сообщения. Также записываются расстояние до конца загруженного окна, непрочитанные, загрузка и причины блокировки прочтения. |
| `chat.message_view.read_decision` | Источник `intersection`, `visible_flush`, `queued_flush` или `loaded_window`; решение `submitted`, `queued`, `blocked`, `failed`; ID, видимая область и `readBlockedReasons` в момент решения. `loaded_window` может подтверждать всё загруженное окно, поэтому не означает видимость каждого ID. |
| `chat.message_view.hidden`, `chat.message_view.closed` | Снимок при уходе в фон/скрытии страницы и последний сохранённый снимок при смене чата; закрытие компонента обновляет снимок, если маршрут тот же. Эти события сохраняются для повторной отправки после перезапуска. |
| `chat.delivery_receipt.queued` | Новые ID в очереди доставки, размер очереди и состояние сокета. |
| `chat.delivery_receipt.emitted`, `.confirmed`, `.failed` | Попытка отправки, положительный ответ сервера либо ошибка/отрицательный ответ. Повтор получает новый `traceId`. Только `confirmed` содержит `serverConfirmed: true`. |

Существующие `chat.read_receipt.emitted` и `chat.read_receipt.received` показывают отправку подтверждения прочтения и получение события сервера. Решение `submitted` не является серверным подтверждением; для проверки сохранения нужны принятый receipt с нужными ID/PTS или `message_reads` в БД.

Для случая «раннее прочитано, позднее нет»:

1. Сверить, знает ли превью ID позднего сообщения и содержит ли его ответ истории, окно отображения и память. Например, отсутствие в ответе сети при наличии в памяти отличается от отсутствия во всех диапазонах.
2. Если позднее сообщение загружено, проверить `visible`, `lastVisible` и `latestKnownMessageSeen`. Положительное значение последнего означает наблюдение в видимой области во время активного приложения. Проверить, к какому `latestKnownMessageId` относится снимок: при смене последнего сообщения флаг сбрасывается.
3. Если нужный ID был видим, проверить `read_decision`, `readBlockedReasons`, очередь, отправленный receipt и принятый receipt. Это отделяет блокировку на клиенте от отсутствующего подтверждения сервера.
4. Для надписи «Не доставлено» проверить постановку в очередь и результат ACK. `deliveryStateMessageCount` показывает, содержала ли история данные нового протокола доставки.

Снимки изменений ограничены одним событием за 1,5 секунды и не повторяются без изменения состояния. Решения о прочтении и переходы жизненного цикла записываются отдельно; одинаковое решение подавляется на 5 секунд. Списки ID ограничены 24 элементами с сохранением начала и конца, полный размер и усечение указаны явно. Короткое появление сообщения между снимками, аварийное завершение приложения или потеря телеметрии возможны: отсутствие ID или события само по себе не доказывает, что пользователь не видел сообщение. Флаг `latestKnownMessageSeen` не доказывает, что человек прочитал текст.
