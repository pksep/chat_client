# Диагностика отправки вложений

Связывать события по `trace_id` одной попытки, затем по `payload.messageId`,
`payload.fileId` и `payload.objectName`. Повтор загрузки получает новый trace,
но сохраняет идентификатор сообщения. Дубли доставки события определять по `id`.

Для обычного HTTP PUT файла и обложки видео записываются:

| Событие | Что означает |
|---|---|
| `upload.storage_put.snapshot` | Начало запроса или состояние при смене сети, видимости, уходе со страницы |
| `upload.storage_put.progress` | Пройден следующий порог 25/50/75/100%; максимум четыре записи на запрос |
| `upload.storage_put.body_sent` | Браузер закончил передачу тела; ответ сервера ещё может ожидаться |
| `upload.storage_put.stalled` | За 30 секунд не наблюдались новые байты, завершение передачи тела или заголовки ответа |
| `upload.storage_put.resumed` | После диагностической паузы снова появилась активность |
| `upload.storage_put.finished` | `success`, `http_error`, `network_error`, `aborted`, `timeout` или `send_exception` |

`phase` отличает `sending_body` от `waiting_response`. Поля `loadedBytes`,
`totalBytes`, `elapsedMs`, `noProgressMs`, `idleMs`, `readyState`, `httpStatus`
и `xhrTimeoutMs` показывают состояние запроса. `loadedBytes` сообщает браузер;
подтверждать фактический приём файла нужно по HTTP-результату и серверным логам.
`httpStatus=null` означает отсутствие доступного HTTP-статуса, а не ответ 0 сервера.

`connectionState.socketConnected` показывает транспорт Socket.IO. Для отправки
через `useChat.uploadFile` дополнительно записываются `sendAvailable`,
`hasWebsocketConnection`, `isWebsocketConnecting`, `browserOnline`,
`effectiveBrowserOnline`, `browserOfflineSignal`, `networkReachable`, `activeCall`.
Так можно увидеть расхождение подключённого сокета и разрешения UI на отправку.
`network.websocket.readiness_changed` дополнительно записывает переход самого
флага готовности, `previousReady`, `ready` и источник в `reason`: обработчик SDK,
HTTP health, browser offline/sync, hard reconnect или инициализация. Здоровые ACK
без изменения флага повторных записей не создают. При переходе создаётся снимок
текущих PUT с причиной `chat-readiness-change`.
Стандартный `context` содержит устройство, видимость и сведения о сети; Android
network callback создаёт снимок всех текущих PUT после обновления native context.

Диагностика паузы работает на всех платформах и не прерывает запрос. Одна
непрерывная пауза создаёт одно событие `stalled`. В фоне таймер приостанавливается;
при возврате фиксируется снимок и проверяется прошедший интервал. Время без
наблюдаемой активности может включать заморозку WebView и само по себе не
доказывает потерю интернета. Политика отмены и повторов остаётся прежней.

События категории `upload` сохраняются в существующей ограниченной очереди
диагностики (до 180 событий всех сохраняемых категорий) до отправки на сервер.
Они переживают reload/перезапуск при доступном localStorage. Координаты из
сохранённого context удаляются; подписанные URL и их query-параметры в новых
событиях не записываются, сохраняется только host цели загрузки.

Крупные multipart-загрузки сохраняют существующие этапы `upload.*`, но новые
события `upload.storage_put.*` с байтами относятся к обычному PUT. Успешный
`finished` не подтверждает доставку сообщения: далее должны завершиться
`upload.complete.success` и отправка сообщения с серверным подтверждением.
